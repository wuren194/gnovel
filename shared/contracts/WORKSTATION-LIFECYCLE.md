# 工位生命周期

本契约只定义工位如何协作。章节执行顺序见 `CHAPTER-PIPELINE.md`，十身份规则见 `G-MULTI-IDENTITY-REVIEW.md`。

约定候选批次由 Router 保管原冻结委托，Planner 从准备阶段声明并阅读实际前章候选输入，Writer 继承同一输入和阶段 A，Editor 逐章完成实际审校；各自语义内容仍由工位给出。候选材料不授正文或事实批准。正式采用沿原逐章收尾，批次中断时一起交还可读成果、身份、问题和原续办位置；不预造未来 state、摘要或批准。具体依赖与转换证据由章节契约拥有。

## 用户阶段与内部任务

用户主流程为设计、写章、修改；对应内部 planner、writer、editor。单向别名由 `shared/registries/workflow.json.userWorkflow` 声明，统一在 `task_prepare.prepare_task` 输入边界归一；内部 ID、artifact owner、promptPlan 与机器 nextAction 不随展示名称更改，不建立第二套状态机。

Router 内部化为状态、授权与恢复编排；Composer 是设计的意图澄清／参考分析子阶段，不写正文；Titler 是修改／定稿的标题子阶段；continuity 是定稿后的连续性确认子阶段；repair 是 Editor 的返修模式。各阶段仍按需装载独立 Skill／plan，不合并成三个巨大提示。

章节只使用 `project prepare --view model` 统一准备。每次重取当前任务的读取入口与契约片段，按当前作用域读取；有视角时必须指定 `--pov-character`，缺项不得凭会话记忆补造。`continue` 只消费现有 `reconcile_workflow(persist=False)` 的下一步；冲突、未授权或须维护／批准的操作显式阻塞，不自动写入或批准。

调用者明确确认仍持有上一份准备报告时，允许只交付变化字段；当前任务、就绪、阻塞和授权边界仍须重新计算并返回。换窗、上下文压缩、引用丢失或作用域变化时完整交付，不把曾经发送当成仍然记得。差量省略不取消原文阅读、契约执行或逐项审查义务。

[M] 成组执行与独立准备使用同一持有基线；登记后刷新也不得把尚未交付的中间报告当成模型已持有。已由准备覆盖的上下文不因差量省略而重复获取。

聚合待办可装配成版本绑定材料，沿原领域状态、依赖、规则与回执读取；每项结论仍由工位提供。依赖展开保持内容选择与 POV 隔离，历史影响不自动变成新增审查义务。下一步的操作与参数只说明如何调用，不构成执行授权；未知语义输入、冲突和作者批准不得由工具补造。

[M] 跨批复核材料只在调用者明确持有回执、当前选择与权限有效时省略同版本的已交付字符；回执须沿实际分页累计，不能把跳页当作已读。已装配的逐项任务仍交付，材料持有不等于审查完成；不能确认持有时重新读取。

[M] 边读边登记的续页只可折叠调用者明确指定、属于同一读取快照且可逐项证明的自身回执变化；其他输入漂移仍拒绝。冻结材料与当前进度分开呈现，不继承批准或补造未审结论。

[M] 模型视图只压缩交付，不减少检查。问题、未知、未检查、授权与执行前提必须保留；通过明细可计数并引用同次完整证据。审校表单引用冻结材料与槽位，工位只交实际填写，工具恢复绑定；缺项仍缺项、过期仍拒绝，不因省略机械字段而省略逐席审查。

## 生命周期矩阵

| 工位 | 准备 | 决策或审查 | 交付 | 不负责 |
|---|---|---|---|---|
| Composer | 读取创作意图与参考资料 | 阶段 A，全席 | 设计候选、EM 卡 | 正文、章节推演 |
| Planner | 读取设定、前章与遗留 | 阶段 A，按契约组席 | 卷/弧线/章推演 | 正文、正式入库 |
| Writer | 读取已批准推演与文风契约 | 无圆桌，执行上游决策 | 纯章节正文 | 项目写入、状态编译、批准 |
| Editor | 运行机械门并读取语义证据 | 阶段 B，全席 | 审校报告、精修稿、状态候选 | 正式入库、擅自重规划 |
| Titler | 读取当前项目标题素材 | 阶段 A，标题固定 5 席（1/2/3/6/10） | 标题候选 | 正文、设定改写、自行定稿 |
| Router | 读取项目状态、授权与请求 | 只检查阶段 A/B 是否完成 | 调度、状态迁移、批准展示 | 复述或替代工位专业规则 |

## 统一执行纪律

1. 工位只读取完成自身职责所需的常驻契约与按需资料；加载计划以 `toolbox.manifest.json` 为准，实际命中由 `novelctl project prompt-plan` 输出并带 hash。
2. 阶段 A 产物先展示，获作者同意后封装为 `stage_a_review` / `title_candidates` 工件并登记。章节推演的 `stage_a_review` 必须绑定当前 sourcePlanHash；批准后使用 `workflow advance --to planned` 推进状态。批量授权与 Level 10 规则按 `CHAPTER-PIPELINE.md` 执行。
3. Writer 只返回纯正文。Router 或调用者用内置提交入口保存、绑定和登记候选，调用真实机械门；advanceLifecycle 仍复用 planned → draft → review 的原门。
4. Editor 只修改已定位的范围；结构问题返回 Planner 或 Writer，不在精修阶段发明新设定。
5. Router 只编排状态与授权，不复制其他工位的提示、检查表或输出骨架；工件批准后必须通过 `workflow finalize-chapter` 才能形成稳定事实。恢复先运行 `workflow recover` 检查中断事务，再使用 `workflow reconcile` 重建唯一下一步。
6. 入库不等于下一章可开工：`finalize-chapter` 登记待确认的连续性批次，作者明确确认后用连续性领域入口登记完成证据；事实回流、引文和摘要各自完成，不能从空状态变化推断无需处理。未完成时下游动作返回 `CONTINUITY_REQUIRED`，不靠会话记忆跳过。工位输入与就绪判断统一由 `novelctl project prepare` 汇总（必读材料、上游证据、缺项、下一步）。

## 工位 Skill 的最小结构

每份工位 `SKILL.md` 只保留五类信息：职责、输入、执行、输出、边界。共享流程、版本历史、阈值和席位规则必须引用真源，不得内联副本。
